# 代码组织与维护

本文是当前代码位置和依赖边界的维护入口。历史开发记录中的旧目录以本文为准。

## 组织原则

保留 HTTP、应用用例、领域契约、持久化、外部集成的分层，每层内部再按业务归类。查找一个功能时，先选业务，再沿请求链查看对应层。目录负责归类；文件负责一个完整职责，不能为了行数把同一职责切成相互依赖的碎片。

前端沿用功能目录，并在较大的功能内区分状态、纯数据转换、界面和交互。组件继续复用已有 shadcn/ui、Tailwind 和主题变量。此轮整理参考了 Mu 的功能与文案组织，以及 deepseek-harness 的协议、投影和轨迹展示分工。

## Agent 位置和运行链路

```text
agent/
├── bootstrap.py             # 产品插件选择与依赖装配
├── core/                    # Kernel、作用域、服务标识、Hook 和通知
├── orchestration/           # 会话 Agent、调度、收件箱、重试、作业和子任务
├── context/                 # 历史组装、运行快照、项目指令和附件上下文
├── compaction/              # 压缩用例、压力计算、选择和提示词组装
├── capabilities/            # 文件观察、模型提供者和计划模式能力
├── plugins/                 # 将能力接入 Kernel 的贡献插件
├── commands/                # 用户命令及作用域注册
├── prompts/                 # 人工维护的指令、文案和严格加载器
├── skills/                  # 技能发现、注册、加载和内置资源
├── mcp/                     # Agent 对 MCP 工具与资源的消费
├── tools/                   # 按 filesystem / context / workflow / maps / oge 分类
└── runtime/
    ├── contracts/           # 模型、工具、内容、Hook、问题和重试契约
    ├── events/              # 按 session / run / assistant / tools / context 定义事件
    │   └── store.py         # 统一事件联合、校验、事件批次和存储协议
    ├── execution/           # Runner、模型步骤、工具步骤和运行策略
    │   ├── model_stream.py  # 流消费、校验和增量提交
    │   └── model_output.py  # 完整工具调用帧校验
    ├── streaming/           # 内容块组装和带时间的流记录
    └── projection/          # 会话、运行、压缩和控制状态投影
        └── run/            # replay / dispatch / lifecycle / budget / assistant /
                            # tools / interactions / guards / snapshot
```

运行链路：HTTP 路由 → 应用用例与会话 Agent → 调度器 → Runner → 模型或工具 → 同事务提交事件与投影 → 事件通知 → 前端状态和展示。

归约器只处理已提交事件；生命周期、预算、助手输出、工具批次、用户交互各有独立处理模块，共用守卫和状态快照。事件存储协议是统一入口，不在各业务中复制事件模型。模型步骤负责调度与失败结算；流消费不拥有重试策略。确认服务负责事务编排，`confirmation_policy.py` 校验精确快照和授权，`confirmation_approval.py` 在调用方事务中执行批准操作并生成事件。

上下文压缩、问题、确认、取消、重试和子任务仍使用原有持久契约。不要在重构时拆开事件、投影和业务副作用原本要求的原子事务。

## 前端和桌面位置

| 功能 | 数据与状态 | 界面与交互 |
| --- | --- | --- |
| 消息 | `features/messages/model/`、`state/` | `rendering/`、`composer/`、`navigation/` |
| 事件与轨迹 | `features/events/stream/`、`projection/`、`trajectory/records/` | `trajectory/`、`trajectory/inspector/`、`trajectory/timeline/` |
| Agent | `features/agent/api.ts`、工具结果解析 | `controls/`、`plan/`、`tools/`、`tools/results/` |
| 地图 | `features/maps/runtime/`、`imagery/` | `conversation/`、`layers/`、已有地图工具栏 |
| 会话归档 | `features/sessions/archive/` | 同目录的归档页和会话组件 |
| 工作区 | `features/workspaces/api.ts`、`files/` | `sidebar/`、已有工作区页面 |
| 中文文案 | `locales/zh-CN/` 中按产品区域拆分 | `index.ts` 统一组装文案对象 |
| 桌面主进程 | `electron/src/main/backend/`、`storage/` | `main/index.ts` 负责窗口和 IPC 装配 |

`SessionMessagesContext` 只发布会话状态；`useMessages` 管理查询和提交，`useMessageSynchronization` 对齐消息事件和查询快照，`model-selection` 计算可用模型。时间轴视图和 `useTrajectoryTimeline` 的手势、缩放、拖动状态分开。轨迹纯记录转换不依赖 React，也不导入界面组件。

## 修改入口

| 要修改的内容 | 优先查看 |
| --- | --- |
| 新增 HTTP 接口 | 对应 `api/<业务>/`，并在 `api/router.py` 注册新路由组 |
| 新增业务操作 | 对应 `application/<业务>/`；共享输入和结果放领域层 |
| 新增或修改表 | `persistence/records/<业务>.py` 与 `persistence/schema.sql` |
| 新增 Agent 事件 | 对应 `runtime/events/`，再更新 `store.py` 联合和对应投影 |
| 修改模型流处理 | `runtime/execution/model_stream.py` 和 `streaming/` |
| 新增 Agent 能力 | 能力实现、`tools/<分类>/`、贡献插件、`agent/bootstrap.py` |
| 修改对话展示 | `features/messages/rendering/`，纯转换放 `model/` |
| 修改轨迹展示 | `trajectory/records/`、`inspector/` 或 `timeline/` |
| 修改界面文案 | 对应 `locales/zh-CN/` 模块 |

## 约束和检查

运行 `npm run check:architecture` 检查业务根目录归属、内部模块路径、依赖方向、事件与运行投影的循环依赖，以及前端纯转换对 UI 的依赖。它是静态架构检查，不会启动服务或访问用户数据。

应用层、Agent 和基础设施不导入 HTTP 层；领域层不导入应用和基础设施；持久化与外部适配不导入应用层。Agent runtime 不依赖 FastAPI、SQLAlchemy 或产品基础设施。运行状态契约可供领域对象引用，不能因此将网络、数据库或产品插件拉入 runtime。

开发时还应运行 `npm --prefix frontend run typecheck`、`npm --prefix frontend run build` 和 `npm --prefix electron run build`。结构性修改需验证后端启动关闭、受影响操作，以及 API、事件和数据库契约。静态检查和构建不能替代真实供应商与远端服务的集成验收。

旧文件和旧导入路径已删除，不提供兼容转发模块。后续新增功能应扩展对应业务目录，已有文件同时承担多个独立职责时再拆分。
