# 模型图片输入

## 2026-10-12 读图失败定位

郑州工作区中 `read_image` 的两次失败都发生在本地图片输入开关检查，尚未读取图片并向供应商发送视觉请求。两次运行分别使用 `deepseek-flash`、`deepseek-v4-pro`，冻结配置均为 `image_input.enabled=false`。旧报错误将本地未启用表述为模型不支持；现在使用 `IMAGE_INPUT_DISABLED`，明确说明设置位置及新消息生效范围。

## 默认值与设置

`domain/model_image_defaults.py` 按供应商类型和完整模型 ID 声明官方确认的视觉模型。首次发现或手动新增模型时采用默认值；刷新目录不会覆盖已有图片开关、像素预算和字节上限。未知模型、第三方聚合服务与自定义模型不猜测视觉能力，可在“设置 → 模型 → 模型参数”中依据实际供应商说明启用。

图片开关表示允许本地发送图片，不是经过视觉推理验证的能力标签。文本、工具连接检查不验证图片能力。修改图片开关不要求重复文本和工具检查；新运行使用新配置，已有运行及历史请求快照不改变。

## 发送路径

用户附件或 `read_image` 生成持久化图片引用，统一内容桥接将原始图片引用解析为 SDK `BinaryContent`。协议编码由已有 SDK 执行：Chat Completions 使用用户消息中的 `image_url` 与 base64 data URL；Messages 使用 `image` 与 `source.type=base64`；Responses 使用 `input_image`。工具返回的文本仍作为工具结果，图片作为随后用户内容发送，避免把图片变成文本 JSON。

后端沿用现有本地限制：`read_image` 源文件最多 16 MiB，默认每张请求图片最多 2 MiB，可在设置中调整至 16 MiB；请求图片按像素预算和字节上限处理，不改写工作区原图。这些是本项目限制，不等同于供应商最大额度。未接入供应商 Files API。

## 核验

通过隔离数据库和本地 HTTP fixture 核验五家供应商的八条接入路径：DeepSeek 的三种 SDK API，Kimi、MiMo、GLM 的 Chat Completions，OpenAI 的 Chat Completions 与 Responses。实际 Agent 调用 `read_image`，后续 SDK 请求包含图片字节，工作区原图不变，运行日志可以重建。核验同时覆盖初始默认值、未知模型保持关闭、手动设置在刷新目录后保留，以及只修改图片设置不清除文本和工具检查。

当前桌面数据库的 `deepseek-flash` 已通过应用服务开启图片输入；四条历史运行快照未改动，`deepseek-v4-pro` 保持关闭。未向供应商发送付费视觉请求，没有新增仓库测试文件。前端构建、Python 编译与变更文件 Ruff 检查通过。
