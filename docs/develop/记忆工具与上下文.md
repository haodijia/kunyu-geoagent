# 记忆工具与上下文

当前 Agent 只注册 `memory_read` 和 `memory_write`。工作空间记忆不自动注入模型请求，只通过工具调用进入会话历史。

## 已确认的问题

本地数据库中的工作空间是 `ll`，其下有 `ss` 和 `新会话`。发生记忆误判的是 2026-10-01 的 `新会话`。

- 请求快照序号 134 的记忆数量为 0。用户批准后，序号 146 的写入结果创建第一条记忆，时间为北京时间 09:27:03。
- 下一次请求快照序号 150 把刚写入的记忆放在所有历史消息之前，模型于是将其误解为对话开始前就存在的记忆。
- 第二条记忆在序号 194 创建，时间为北京时间 09:27:43；序号 198 再次把最新的两条记忆放到历史之前。
- 两次写入都实际创建了记录，并非内容去重。旧实现只有工具调用 ID 的执行幂等约束，没有按记忆内容去重。
- 旧检索工具不能列出记忆，模型为“有什么记忆”猜测关键词。筛选后的匹配数量也被混同为工作空间总量。

当前实现移除了自动记忆注入及重复读取工作空间的工具。记忆读写结果按原有工具调用顺序保留，不把更新后的存储内容前置为过去的背景。

## 工具

| 工具 | 参数 | 行为 |
| --- | --- | --- |
| `memory_read` | `query` 默认空字符串；`limit` 默认 20，范围 1–20 | 空查询列出最近记忆；非空查询按字面子串筛选。`total_count` 是匹配总数，`returned_count` 是实际返回数量，`truncated` 表示仍有未返回的匹配项。 |
| `memory_write` | `content`，1–2,000 字符 | 提交要保存的原文，应用展示确认卡；批准后在同一事务中创建记忆并记录工具结果。 |

工作空间范围始终由后端绑定。模型不能传入另一工作空间的标识。写入确认继续由应用处理。

## 手动修改入口

- **系统提示词**：`backend/src/kunyu/agent/prompts/system.md`。使用中文，说明当前读写工具、查询计数、确认卡及历史工具结果的时间含义。直接编辑文本；每次模型请求重新读取，下一次请求生效。空文件或读取失败会报错。
- **上下文组成及顺序**：`backend/src/kunyu/application/agent_context.py` 的 `ScopedAgentContextProvider.build()`。当前顺序为系统提示词 → 工作空间与地图上下文 → 当前会话历史 → 手工注入上下文。
- **工作空间与地图内容**：同文件的 `_scope_prompt()`。
- **历史消息拼接**：同文件的 `build_model_history()`，从事件序号重建用户、助手及完整工具结果。
- **地图数据来源**：`frontend/src/features/sessions/map-context.ts` 构造数据；`frontend/src/features/messages/api.ts` 随用户消息提交；后端保存到 Run 的地图快照。
- **工具参数和描述**：`backend/src/kunyu/application/local_tools.py`。工具描述保留原文，由用户自行修改；读取工具当前支持空查询列出记忆，但原描述仍只介绍子串检索。

现有 `POST /api/v1/sessions/{session_id}/context` 可提交 `{"content":"补充上下文"}`，需要桌面会话认证。此入口当前用于单次请求补充：`backend/src/kunyu/persistence/agent_context.py` 仅加载最后一次请求快照之后的 `context.injected` 事件；它不是系统提示词编辑器，也不会在后续每轮自动保留。

修改 Python 上下文代码后需重启开发服务。既有聊天、记忆及请求快照保留原始记录；旧回复中的误判不会被自动改写。重新开始会话可避免继续引用那段错误回复。
